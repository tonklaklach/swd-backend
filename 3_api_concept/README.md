# API Concept

## Idempotency

Idempotency หมายถึงการเรียก API เดิมด้วยข้อมูลเดิมซ้ำแล้ว ผลสุดท้ายของข้อมูลยังเหมือนเรียกครั้งเดียว เรื่องนี้มีประโยชน์เวลาที่ client ไม่แน่ใจว่า request สำเร็จหรือยัง เช่น ส่งคำขอไปแล้ว timeout จึงต้องลองส่งใหม่

ตัวอย่างในงานนี้คือ PUT แก้ไขโรงเรียน ถ้าส่งชื่อ ตัวย่อ และที่อยู่ชุดเดิมไปที่โรงเรียน ID เดิมสองครั้ง ข้อมูลสุดท้ายก็ยังเป็นโรงเรียนรายการเดิมที่มีค่าตามที่ส่งมา

โค้ด Go ด้านล่างแสดงการใช้ UPDATE ตาม ID ซึ่งเป็นแนวทางเดียวกับที่ใช้ใน repository ของโปรเจกต์

```go
func replaceSchool(ctx context.Context, db *sql.DB, id int64, name, abbreviation, address string) error {
    result, err := db.ExecContext(ctx,
        "UPDATE schools SET name=?, abbreviation=?, address=? WHERE id=?",
        name, abbreviation, address, id)
    if err != nil {
        return err
    }
    count, err := result.RowsAffected()
    if err != nil {
        return err
    }
    if count == 0 {
        return sql.ErrNoRows
    }
    return nil
}
```

DELETE ก็มีคุณสมบัตินี้ได้ แม้ครั้งแรกจะตอบ 204 และครั้งถัดไปตอบ 404 เพราะผลสุดท้ายคือรายการนั้นถูกลบออกไปแล้วเหมือนกัน

ส่วน POST สร้างโรงเรียนในโปรเจกต์นี้ หากเรียกซ้ำจะสร้างรายการใหม่ได้ ถ้าต้องการให้ retry ได้โดยไม่สร้างซ้ำ สามารถออกแบบให้ client ส่ง Idempotency-Key มาด้วย แล้วเก็บ key และผลการทำงานไว้ในฐานข้อมูล เมื่อได้รับ key เดิมกับข้อมูลเดิมก็คืนผลเดิม

การเก็บ key ควรทำพร้อมกับการบันทึกข้อมูลใน transaction เดียวกัน และมี unique constraint ป้องกัน request ที่เข้ามาพร้อมกัน ถ้า key เดิมถูกใช้กับข้อมูลคนละชุดควรตอบ conflict ส่วนการเก็บ key ไว้ใน memory อย่างเดียวจะมีปัญหาเมื่อ restart หรือรันหลาย instance

## JSON เทียบกับ Protocol Buffers

JSON เป็นข้อความที่อ่านได้โดยตรง จึงดู request และ response ตอน debug ได้ง่าย และใช้กับ browser, curl หรือ Postman ได้สะดวก ข้อแลกเปลี่ยนคือมีชื่อ field อยู่ในข้อมูลที่ส่งด้วย ทำให้ขนาดอาจมากกว่ารูปแบบ binary ถ้าต้องการตรวจโครงสร้างให้เข้มงวดก็ต้องกำหนด schema หรือ validation เพิ่ม

Protocol Buffers ใช้ไฟล์ .proto กำหนดชนิดข้อมูล แล้ว generate code สำหรับแต่ละภาษา ข้อมูลที่ส่งเป็น binary ซึ่งมักมีขนาดเล็กกว่า JSON แต่ต้องใช้ schema และเครื่องมือช่วยอ่าน จึงมีขั้นตอนในการพัฒนาและ debug เพิ่มขึ้น

อีกเรื่องที่ต้องระวังคือการแก้ schema ของ Protobuf ต้องรักษา field number เดิม และไม่เอาหมายเลขของ field ที่ลบไปกลับมาใช้กับข้อมูลใหม่ เพื่อให้บริการที่ยังใช้ schema คนละเวอร์ชันสื่อสารกันได้ ส่วน JSON ก็ต้องระวังการเปลี่ยนชื่อ field หรือชนิดข้อมูลที่ client เดิมใช้อยู่เช่นกัน

สำหรับ API ที่ต้องให้คนภายนอกหรือ frontend เรียก JSON ใช้งานได้สะดวก ส่วนการสื่อสารระหว่างบริการที่ต้องการ schema ชัดเจนและรองรับ code generation หลายภาษา Protobuf ก็เป็นตัวเลือกที่เหมาะสม หากเหตุผลหลักคือเรื่องความเร็วหรือขนาดข้อมูล ควรวัดกับข้อมูลและการใช้งานจริงก่อนตัดสินใจ

ในโปรเจกต์นี้เลือก JSON เพื่อให้ตรวจ API และอ่านผลลัพธ์ได้ง่าย
